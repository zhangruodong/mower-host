# 上下位机架构

## 分工

```
  上位机（树莓派 5B / Debian Bookworm）                             下位机（STM32F407VE + FreeRTOS）
┌──────────────────────────────────────────────┐                  ┌──────────────────────────────────┐
│  决策                                        │                  │  执行                            │
│   · SLAM (slam_toolbox)                      │                  │   · 1000 Hz 姿态/速度环          │
│   · Nav2 (AMCL + Smac + MPPI)                │                  │   · 电机 PID、编码器读取         │
│   · 视觉 (YOLOv8 + AprilTag)                 │                  │   · IMU 采样、电压采样           │
│   · PyQt5 界面                               │                  │   · 急停锁存                     │
│                                              │                  │   · 舵机 / 回充 / 自检           │
│  融合                                        │                  │                                  │
│   · robot_localization (EKF) → /odom_combined│                  │                                  │
│                                              │                  │                                  │
│  桥  mower_bridge / chassis_bridge           │◄──UART3 115200──►│                                  │
└──────────────────────────────────────────────┘                  └──────────────────────────────────┘
```

**分界线就是串口**。下位机保证「给我速度我能跑」，上位机负责「往哪跑」。所有实时性要求高的东西（电流环、姿态解算、急停）在下位机；所有要操作系统、要网络、要摄像头的东西在上位机。

速度是**车体系**（Vx 前 / Vy 左 / Vz 逆时针），**单位 mm/s**。上位机不做运动学——STM32 已经算好车体速度了，不需要轮距轮径。

## 数据流

**下行**：界面键盘 / Nav2 → `/cmd_vel` → 桥组 11 字节帧 → UART → STM32

**上行**：STM32 20 Hz 发 24 字节 → 桥解析 → 三个话题发给整个 ROS 图

| 桥发布 | 类型 | frame_id | 谁在用 |
|---|---|---|---|
| `/odom` | `nav_msgs/Odometry` | `odom_combined → base_footprint` | EKF (`odom0`) |
| `/imu/data_raw` | `sensor_msgs/Imu` | `gyro_link` | EKF (`imu0`) |
| `/PowerVoltage` | `std_msgs/Float32` | — | 界面电量显示 |

桥**不发 TF**。`odom_combined → base_footprint` 那个变换由外部的 `robot_localization` ekf_node 出（`ekf.yaml` 里 `publish_tf: true`）。

### 关于 ekf.yaml

`ekf.yaml` 是**配置不是代码**，能直接用，而且参数是要调的。里面的关键约定桥必须照着来，否则 EKF 不出 TF：

- `odom_frame: odom_combined`、`base_link_frame: base_footprint`
- `odom0: odom`、`imu0: /imu/data_raw`
- `imu0_config` 里 **yaw = true** → **四元数必须是真算出来的**，这就是桥里要有一个 Mahony 互补滤波的原因（`bridge/mower_bridge/protocol.py` 里的 `Mahony` 类）
- `odom0_differential: true` 且只融合 `x_vel, y_vel, yaw_vel` → **里程计的绝对位置漂移无所谓**，只要增量对
- EKF 的输出 `/odometry/filtered` 被 launch 重映射成 `/odom_combined`

里程计就是 `Robot_Pos += Robot_Vel × dt` 的欧拉积分，四个修正系数（`odom_*_scale`）默认全 1.0——**等于没标定过**。保留成参数当标定旋钮：实测走 1 m 差多少，按比例改。

## 为什么看门狗必须由桥来兜

固件里其实**有**指令丢失保护（`balance_task.c:58-64`：超时了就把速度归零）。可惜它挂在一个开关
后面：`SysVal.SecurityLevel == 0`。而 `sys.c:41` 把这个值默认设成了 **1**，注释原话是
「指令丢失后按最后一次速度指令运动」。全固件再没有第二处给 `SecurityLevel` 赋值。

从上位机这边也够不着它：

- 下行帧里 `[2]` 是唯一空着的位置，可固件 `uartx_callback.c` 通篇没读过 `frame[2]`，往里塞
  什么都不管用；
- 也没有别的命令字能碰到这个变量。

也就是说，**这道保护永远不会生效**。界面卡死了、Nav2 崩了、SSH 断了、网线被踢了——只要上位机
不再发速度指令，车就会按最后那个速度一直跑下去。

这个活儿只能由桥来干：`/cmd_vel` 超过 `cmd_vel_timeout`（默认 0.5 s）没来新指令，就主动补一帧
零速度；节点退出（Ctrl-C）前也补一帧。

为什么非得是桥？因为所有速度指令，不管从界面来还是从 Nav2 来，都得经由它写串口，一条也绕不开。
在这儿兜一次就够了；要是放在界面里兜，Nav2 那条路就漏了。


## 边界与约束

- **串口同一时刻只能有一个进程开**：`chassis_bridge` 起来了，别的底盘节点就不能再开，后开的那个抢不到 `/dev/mower_chassis`。
- **上电后 10 秒内 STM32 丢弃所有指令**（`CONTROL_DELAY`），见 [协议.md](协议.md) 第三节。
- **急停锁存**，只能靠 `CMD=8` 解，界面主页面有「解除急停」。
- **桥不解析** 19 字节超声波帧和 8 字节回充帧——割草机没这两个硬件。
- **两条速度来源会打架**：手动控制的键盘和 Nav2 都往 `/cmd_vel` 发。界面在手动页会提示，但**没有互锁**。
